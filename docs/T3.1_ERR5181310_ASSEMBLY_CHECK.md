# T3.1 assembly-correctness check — ERR5181310 (SARS-CoV-2)

**Status: IN PROGRESS. QUAST still running. This file records what is measured
so far and what is still pending — nothing here is a final verdict.**

## The three things involved, and who grades who

There are three separate things. Do not conflate them.

1. **The real virus genome** — NC_045512.2, 29,903 bp. This is the answer key.
   Fetched from NCBI, verified as the correct accession/length.
2. **Our output** — the pseudogenome our tool exported from the archive.
3. **SPAdes' output** — the assembly SPAdes produced from the same reads.

**Neither tool grades the other. Neither tool grades itself.** SPAdes does not
check its own output against a reference — confirmed: SPAdes only assembles,
it has no built-in correctness check. Our tool doesn't either.

**QUAST is the grader.** It is a separate, independent tool. It aligns BOTH
outputs against the real genome (item 1) and reports how much of the true
genome each one actually reconstructed, and whether either contains errors
(misassemblies, mismatches). QUAST is running now; this is what item "Task #5"
below refers to.

## What is measured so far (raw output, before grading)

| | length | pieces | notes |
|---|---|---|---|
| true genome | 29,903 bp | 1 | ground truth, NC_045512.2 |
| **ours** | 24,072,995 bp | 2 (main 24,066,046 bp + second region 6,949 bp) | ~805x the true genome length, in one giant piece |
| **SPAdes** | 50,211 bp raw / 27,966 bp after QUAST's length filter | 183 contigs | largest single contig 7,292 bp = 24% of the true genome |

**Neither number alone proves correctness.** Ours is wildly oversized (likely
redundant/duplicated content, not necessarily missing anything). SPAdes is
close to the right total size but fragmented into 183 pieces, so it may be
MISSING most of the genome rather than just breaking it into parts. Which
failure is worse is exactly what QUAST's genome-fraction and misassembly
numbers will settle. **Not decided yet.**

## Why our output is 800x oversized here — mechanism, not yet fully traced

Our encoder's exact-duplicate collapse already removed ~92% of reads
(1,825,142 in -> 152,085 unique). The remaining 152,085 reads are still
NEAR-duplicates of each other (same 30kb genome, extreme amplicon-sequencing
depth, differing by sequencing noise or true minor variants) -- exact-hash
dedup cannot merge these.

**Working hypothesis, not yet confirmed by tracing the actual code path:**
greedy overlap chaining assumes overlap length/quality reliably signals "this
read is the next genuinely new piece of the genome." At this depth/genome-size
ratio, many unrelated reads overlap the growing chain's tail well enough by
chance, so the chain keeps extending instead of terminating -- it strings
together nearly the entire 152,085-read pool into one path (152,085 x ~150bp
~= 24,000,000, which matches PG_LEN almost exactly).

This is a hypothesis grounded in the log numbers, not a confirmed root cause.
Confirming it requires instrumenting the actual round1/round2 chaining loop in
`stages/106_inprocess.cpp` on this dataset -- **not done yet.**
